# LOCO loyalty sender identity - 2026-11-11

Reported: LOCO enrollment messages appeared from the platform owner's number. Read-only provider history confirmed one recent LOCO message on the platform sender and newer LOCO messages on the verified brand sender. The stored connection is connected and explicitly opted in; requested, verified and provider account phones match

Cause: the shared sender selector intentionally fell back to platform primary/backup whenever brand credentials or account health could not be verified. This fallback applied to wallet welcomes and cashier-created card links. A transient provider429 was observed during this investigation; it proves such a check can fail even while the linked account is authorized, but the historical message's exact failure cause is not logged

Fix: both loyalty workers now use selectLocoLoyaltySender, which returns only the verified opted-in LOCO instance or null. Unavailable, rate-limited, disconnected, mismatched, invalid and missing connections never select a platform sender. Existing SQL claim filters leave LOCO jobs pending when its sender is unavailable; other brands continue on their existing sender. Queue expiry, deduplication, leases, Google save checks and uncertain-POST semantics remain unchanged. Existing OTP/document fallback is preserved outside this requested loyalty scope. Connection and disconnect copy now explain the distinction

Checks:45 routing cases; wallet welcome/dedupe/Apple-Google handlers;15 read-server groups including pending-offline/recovery;23 brand-phone UI groups; real local Postgres delivery/full queue rollback suites with11 inherited entitlement checks; TypeScript, text integrity and scoped server lint PASS on Node24.19.0. Live read-only function metadata confirms both claim functions require brand health for LOCO and retain service-only execution. Live new selector returned null on provider429 without platform fallback. Before changing code, live account checks selected the matching brand and history showed recent sent/delivered messages from it

No customer messages, manual dispatch, resends, pairing, configuration changes or database mutations performed. No browser/device claim.
